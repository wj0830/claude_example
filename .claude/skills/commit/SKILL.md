# 커밋 스킬

Git 변경사항을 사람이 직접 정리한 것처럼 논리적 단위로 나누고, 그룹마다 Conventional
Commits 형식의 한국어 커밋 메시지를 붙여 커밋하는 절차다. 목표는 "무엇을 바꿨는지"가
아니라 "왜 이 변경들이 하나로 묶이는지"가 커밋 로그만 보고도 드러나게 하는 것이다.

## 왜 이런 절차가 필요한가

diff를 훑어보고 바로 `git commit -am "update"` 하는 것보다, 변경사항을 의미 단위로
쪼개서 각각 리뷰 가능한 크기의 커밋으로 만들면 나중에 `git blame`이나 `git bisect`,
코드 리뷰가 훨씬 쉬워진다. 이 스킬은 그 정리 작업을 대신 해주는 것이지, 단순히
커밋 명령어를 실행해주는 것이 아니다. 그래서 그룹 분리와 메시지 초안 작성에
공을 들이고, 실제 `git commit` 실행 전에는 항상 사용자 확인을 거친다.

## 절차

### 1단계 — 현재 상태 파악

```
git status
git diff
git diff --staged
```

- 저장소가 아니면(`fatal: not a git repository`) 사용자에게 알리고 중단한다.
- 변경사항(수정/추가/삭제/untracked 포함)이 전혀 없으면 그 사실을 알리고 종료한다.
- merge conflict 마커가 있는 파일이 있으면 커밋 전에 충돌 해결이 필요하다고
  안내하고 중단한다. 충돌을 대신 해결하려 하지 않는다.
- `.env`, `*.pem`, `credentials*`, `*secret*` 처럼 비밀값을 담고 있을 가능성이 큰
  파일이 변경 목록에 있으면, 자동으로 add하지 말고 사용자에게 먼저 확인받는다.

### 2단계 — 논리적 단위로 분류

변경된 파일과 hunk들을 훑어보고, "같은 이유로 함께 바뀐 것"들을 그룹으로 묶는다.
판단 기준은 파일 위치가 아니라 **의도**다:

- 새 기능 추가와 그 기능의 테스트 → 같은 그룹
- 기능 추가 도중 우연히 발견한 무관한 버그 수정 → 별도 그룹
- 포맷팅/린트 자동 수정처럼 의미 없는 변경 → 별도 그룹(가능하면 별도 커밋으로 분리해
  실제 로직 변경 커밋을 깨끗하게 유지)
- 리팩터링과 그 리팩터링이 필요했던 기능 변경이 뒤섞여 있다면, 가능한 선에서
  분리한다. 완전히 분리할 수 없는 diff(같은 함수 안에서 로직과 리팩터링이 얽힌 경우)는
  무리하게 쪼개지 말고 하나로 묶되, 커밋 메시지에서 그 사실을 설명한다.

그룹이 하나뿐이면(변경사항이 애초에 한 가지 의도로만 이루어져 있으면) 커밋도
하나만 만든다 — 억지로 여러 개로 쪼개지 않는다.

### 3단계 — 그룹별로 스테이징 + 메시지 작성 + 커밋

그룹마다 다음을 반복한다:

1. **스테이징**: 해당 그룹에 속한 파일/hunk만 `git add`한다. 한 파일 안에 서로
   다른 그룹의 변경이 섞여 있으면 `git add -p`로 hunk 단위로 나눠 담는다.
2. **커밋 메시지 작성**: Conventional Commits 타입 중 하나를 고르고, 한국어로
   간결한 요약을 붙인다. 아래 "커밋 메시지 형식" 참고.
3. **사용자 승인**: 이번 그룹에 포함된 파일 목록과 작성한 커밋 메시지를 보여주고
   확인을 받는다. 사용자가 메시지를 수정하거나 그룹을 다시 나누라고 하면 반영한다.
   여러 그룹이 있다면 전체 계획(몇 개의 커밋으로 나눌지, 각각 무엇을 담을지)을
   먼저 한 번에 보여주고 승인을 받은 뒤, 순서대로 커밋해도 된다.
4. **커밋 실행**: 승인 후에만 `git commit`을 실행한다. pre-commit hook이 실패하면
   `--no-verify`로 건너뛰지 말고 원인을 고쳐서 다시 커밋한다.

### 4단계 — 결과 요약

모든 그룹을 커밋한 뒤 `git log --oneline -n <생성한 커밋 수>`로 결과를 보여주고
간단히 요약한다.

## 커밋 메시지 형식

```
<type>: <한국어 요약>
```

타입은 Conventional Commits 표준을 그대로 사용한다:

| type | 의미 |
|---|---|
| feat | 새로운 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 코드 구조 개선 |
| perf | 성능 개선 |
| docs | 문서만 변경 |
| style | 포맷팅, 세미콜론 등 동작에 영향 없는 스타일 변경 |
| test | 테스트 추가/수정 |
| build | 빌드 시스템, 의존성 변경 |
| ci | CI 설정 변경 |
| chore | 위 어디에도 안 맞는 잡다한 유지보수 작업 |

요약은 "무엇을"보다 "왜"를 담을 때 더 유용하다 — 코드를 보면 무엇이 바뀌었는지는
알 수 있지만 왜 바뀌었는지는 diff만으로 알기 어렵기 때문이다. 다만 한 줄 요약에
다 담기 힘들면 본문에 이유를 덧붙인다.

**예시 1**
변경: 로그인 폼에 이메일 형식 검증 추가
```
feat: 로그인 폼에 이메일 형식 검증 추가
```

**예시 2**
변경: null 체크 누락으로 발생하던 크래시 수정 (원인 설명 필요)
```
fix: 사용자 프로필이 없을 때 발생하는 크래시 수정

프로필 조회 결과가 null인 경우를 처리하지 않아 신규 가입 직후
접근 시 크래시가 발생했다.
```

**예시 3** (여러 그룹으로 분리되는 경우)
```
feat: 상품 목록에 페이지네이션 추가
fix: 페이지네이션 작업 중 발견한 정렬 버그 수정
chore: 사용하지 않는 lodash 의존성 제거
```

커밋 메시지 마지막 줄에는 아래를 추가한다(이 저장소의 다른 커밋들과 동일한 관례):

```
Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
```

## 지켜야 할 안전 원칙

- `git commit`은 항상 사용자 승인 이후에만 실행한다. 승인 없이 먼저 커밋하지 않는다.
- `--no-verify`, `--no-gpg-sign` 등 검증을 건너뛰는 옵션은 사용자가 명시적으로
  요청하지 않는 한 사용하지 않는다.
- `git commit --amend`, `git reset --hard`, `git push --force` 등 기존 이력을
  바꾸거나 되돌리는 명령은 사용자가 명시적으로 요청한 경우가 아니면 사용하지 않는다.
  이 스킬의 기본 동작은 항상 **새 커밋을 추가**하는 것이다.
- `git add -A`, `git add .` 처럼 전체를 한 번에 스테이징하는 명령은 피하고, 파일을
  이름으로 지정하거나 `git add -p`로 필요한 부분만 스테이징한다 — 의도치 않게
  `.env`나 빌드 산출물이 커밋에 섞여 들어가는 것을 막기 위해서다.
- 이 스킬을 실행한다고 해서 자동으로 push하지 않는다. push는 사용자가 별도로
  요청했을 때만 한다.
