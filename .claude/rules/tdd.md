# TDD Rule

⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라**

프로젝트의 CLAUDE.md 또는 AGENTS.md에 TDD 관련 규칙이 있으면 **그것을 우선 적용**한다. 이 파일은 기본값(fallback)이다.

---

## 1. 적용 기준 구분

### TDD를 반드시 적용해야 하는 대상

- **비즈니스 로직** — 핵심 알고리즘, 데이터 변환, 규칙 판정
- **API 핸들러 & 라우터** — 엔드포인트 동작, 요청/응답 검증
- **유틸 함수** — 재사용 가능한 헬퍼, 포매터, 파서
- **에러 처리** — 예외 발생 조건, 폴백 로직
- **버그 수정** — 발견된 버그마다 실패하는 테스트 먼저 작성

### TDD가 불필요한 대상

- **타입 정의** — TypeScript 인터페이스, enum, type alias
- **설정 파일** — tsconfig.json, vite.config.ts, eslint.config.js 등
- **순수 UI/뷰** — 렌더링 로직만 있는 컴포넌트 (외형 테스트는 수동 확인)
- **SQL/쿼리** — 직접 실행 후 수동 검증 (데이터베이스 구조가 확정되어야 함)
- **마이그레이션** — 한 번만 실행되는 초기화 스크립트

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

1. **하나의 동작 = 하나의 테스트**
   - 여러 기능을 섞지 않는다
   - 테스트 케이스명은 "should_입력_예상결과" 형식

2. **반드시 먼저 실행해서 실패 확인**
   - 테스트 스윗을 실행하면 **명확하게 빨간색(FAIL)**이어야 함
   - "이미 구현되어 있을 거야" 가정 금지

3. **실패 이유가 "기능 미구현"이어야 함**
   - 구문 에러(import 누락 등)는 OK
   - 하지만 **로직 테스트를 통과하지 못하는 상태**여야 함

### GREEN: 최소한의 코드로 통과

1. **YAGNI 원칙을 엄격히 적용**
   - "나중에 쓸 것 같은" 코드는 쓰지 않는다
   - 테스트가 요구하는 동작만 구현

2. **신규 + 기존 테스트 모두 통과 확인**
   - `npm run test` (또는 `bun run test`)를 실행해서 전체 테스트가 초록색(PASS)
   - 한 줄의 "참고용 하드코딩"도 금지

3. **품질은 나중에**
   - 깔끔한 이름, 최적화, 에러 처리는 REFACTOR에서 한다
   - GREEN은 오직 "작동"에만 집중

### REFACTOR: 코드 품질 개선

1. **GREEN을 유지한 상태에서만 진행**
   - 테스트를 계속 통과시켜야 함
   - 매 단계마다 테스트를 실행해서 확인

2. **세 가지 리팩터만 허용**
   - 중복 코드 제거 (DRY)
   - 변수/함수 이름 개선
   - 헬퍼 함수 추출

3. **새로운 동작 추가 금지**
   - "이 김에 이 기능도 추가할까?" ➜ **금지**
   - 새 기능은 RED로 돌아가서 새 테스트부터 시작

4. **복잡도 감소**
   - 함수 길이, 순환 복잡도, 매개변수 수 검토
   - 타입 안정성 강화 (TypeScript strict 모드)

### 반복

완료된 REFACTOR 후 → 다음 동작에 대해 **RED로 돌아가기**

## 3. 삭제 강제 규칙

### 테스트 없이 프로덕션 코드를 먼저 작성했다면

1. **전부 삭제하고 RED부터 재시작**
   - "어차피 맞는 코드니까 테스트는 나중에" ➜ **금지**
   - 파일을 지웠다가 다시 쓰는 게 더 빠름

2. **"참고용으로 남겨두겠다"도 금지**
   - 주석 처리, 다른 파일에 백업, git stash 후 미루기 ➜ **모두 금지**
   - 마음의 부담이 생기고 RED 단계를 건너뛰게 됨

### 이미 통과 중인 테스트에 코드를 추가했다면

- 기존 테스트가 여전히 통과하는지 확인
- 새 기능이 필요하면 새 테스트(RED)부터 시작

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드일수록 테스트 작성이 빠르다. 실제로 "간단할 것 같은" 부분에서 버그가 숨어있다. |
| "나중에 추가하겠다" | 테스트 없이 코드를 수정하면 실제로 추가하지 않거나, 추가할 때 기존 기능을 깨뜨린다. RED-GREEN-REFACTOR 사이클이 가장 빠르다. |
| "시간이 없다" | TDD는 생각이 정리되면서 개발 속도가 올라간다. 나중에 버그 찾고 수정하는 시간이 훨씬 크다. |
| "삭제하면 이미 한 일이 낭비된다" | 코드는 프로덕션 배포되거나 테스트로 검증되어야만 "일"이다. 테스트 없는 코드는 언제든 사라질 수 있는 임시 상태다. |
| "프로토타입이니까 괜찮다" | 프로토타입이 프로덕션으로 승격되는 순간 TDD 없는 코드의 기술 부채가 폭발한다. 처음부터 TDD로 진행하는 게 프로토타입도 안전하다. |

## 5. 프로젝트별 규칙 우선 조항

프로젝트 루트의 **CLAUDE.md** 또는 **AGENTS.md**에 TDD 관련 규칙이 명시되어 있으면:

- 그 규칙을 **최우선으로 따른다**
- 이 파일(`~/.claude/rules/tdd.md`)의 내용보다 프로젝트 로컬 규칙이 우선

**확인 순서:**
1. 현재 프로젝트 CLAUDE.md의 "Test" 섹션
2. 현재 프로젝트 AGENTS.md의 "Test Boundary" 섹션
3. 위의 두 파일에 규칙이 없으면 이 파일 적용
